## Code Agent

### 1. Compiler-Grounded Hierarchical Diagnosis for LLM-Based Triton Kernel Optimization

- 方向：Code Agent / execution-feedback loop / compiler-grounded diagnosis
- 综合分：4.70
- 链接：https://arxiv.org/abs/2607.23089
- 证据来源：PDF 前 8 页。

**问题背景**：现有 LLM kernel agent 往往把“编译通过了吗、跑得快不快”当成主要反馈。这些信号能告诉 agent 结果慢，却很难告诉它为什么慢，尤其是在 Triton 到 NPU backend 的编译链里，性能问题可能来自源码控制流、IR lowering、memory layout、同步插入或 backend pass。论文把 kernel 优化重新定义为跨层诊断问题，而不是纯文本搜索问题。

**核心方法**：系统采用分层升级流程：先做轻量 pattern triage，再做 profiling diagnosis；只有当浅层证据不足时，才进入 IR attribution 和 compiler-grounded analysis。每一轮都要经过正确性测试和 benchmark 验证，agent 的 rewrite 需要有 profiling/IR/编译器证据支撑。直观地说，它不是让 Code Agent “看到慢就改代码”，而是让 agent 先把慢的症状定位到中间表示和编译 pass，再决定源代码应该怎样重写。

**创新点**：最大价值是把执行反馈细化成可追溯诊断链。对 Code Agent 训练来说，这比单纯保存 error log 或 benchmark 分数更强：训练样本可以包含 runtime symptom、profile trace、IR evidence、compiler question、source rewrite 和验证结果，让模型学习“为什么这个补丁有效”。

**实验与 benchmark**：论文在 NPUKernelBench-derived Ascend 950 suite 上评估，使用 OpenCode agent + DeepSeek V4 Pro，最终有 37 个成功转换的 operator，每个 operator 取 5 个 benchmark case，共 185 个 case。报告的几何平均 speedup 为 4.35x，中位 speedup 为 2.73x；37 个条目中 22 个超过 2x，13 个超过 5x。作者也明确说明分布很不均匀，深层 IR/编译器分析更多是诊断和拒绝机制，不是每个 case 都一定触发。

**可迁移价值**：非常适合转化成 Code Agent post-training 数据格式：把“运行测试 -> 性能剖析 -> IR 证据 -> 修改 -> 再验证”保存成多阶段轨迹。也适合构造 repo-level performance bug benchmark，要求 agent 给出证据而不只是 patch。

**局限**：评估集中在 Triton/Ascend NPU；深层诊断流程是否泛化到 CUDA、CPU、普通仓库级性能问题，还需要更多消融和跨平台验证。

### 2. Imprompt: A Language Framework for Prompt Programming

- 方向：General Agent / prompt programming / structured prompting
- 综合分：4.49
- 链接：https://arxiv.org/abs/2607.22683
- 证据来源：PDF 前 8 页。

**问题背景**：Prompt engineering 已经从写自然语言提示演化到 prompt programming，但很多框架把任务描述、执行细节、输出约束、模型调用策略混在一起。这样做会让 prompt 难以复用，也不利于把 Agent 任务拆成可检查的控制面。

**核心方法**：Imprompt 主张 prompt program 只应包含任务描述，底层 execution detail 交给 compiler。论文把 structured prompting 拆成两层：上层是描述任务的 prompt program，下层是把它编译成具体模型可执行提示的 compiler；还讨论了 prompt typing，把类型检查与 constrained decoding 联系起来。

**创新点**：这篇不是新的 Agent benchmark，而是给 prompt-as-program 提供 PL 视角。它的启发是：Agent scaffold 也可以做成“声明式任务程序 + 编译器”，把任务约束、工具接口、输出 schema 和模型上下文注入分离。这样训练数据可以更稳定，执行 runtime 也更可替换。

**实验与 benchmark**：PDF 前 8 页显示作者实现了 compilers 和 type checkers，并在多种 case studies 上评估；前 8 页未完整列出所有 case study 的数值结果，因此这里不编造具体 benchmark 分数。

**可迁移价值**：适合用于设计 Agent 任务 DSL：用户目标、工具契约、输出 schema、验证器可以是声明式层；具体 prompt、few-shot、constrained decoding 是编译层。对长上下文 Agent 尤其有用，因为它能减少 prompt 模板膨胀。

**局限**：目前更偏语言框架和形式化论证，不是完整的工具 Agent 训练系统。

### 3. FlowLog: Re-thinking Datalog for Fast and Extensible Static Analysis

- 方向：Code Agent / static analysis infrastructure
- 综合分：4.17
- 链接：https://arxiv.org/abs/2607.23971
- 证据来源：PDF 前 8 页。

**问题背景**：Datalog 常用于 points-to analysis、borrow checking、call graph 等静态分析，但真实开发过程不是只跑一次分析。用户会改 facts、调 rules、看瓶颈、做增量更新，甚至需要标准 Datalog 表达不了的语义。传统引擎经常在效率和可扩展性之间取舍。

**核心方法**：FlowLog 把 Soufflé-style Datalog 编译到 Differential Dataflow executable，使同一份分析可以一键切换 one-shot、incremental maintenance 和 profiling 模式。它还提供浏览器 profiler 暴露 per-operator cost，帮助用户修复 bad join order，并展示了 k-core 这类超出标准 Datalog 单调语义的扩展。

**创新点**：对 Code Agent 的价值在于“分析工具可交互化”。如果 agent 能在修复仓库时增量更新静态分析结果、查看 join/profiling 瓶颈、局部撤销 facts，它就不必每次从零跑全量分析。这很适合作为 agentic debugging runtime 的底层能力。

**实验与 benchmark**：论文使用 24 个来自真实 workload 的 benchmark，覆盖 DOOP points-to 和 Polonius-style borrow checking。PDF 报告 FlowLog 在所有 24 个 benchmark 中最快；DOOP 上相对 Soufflé 中位 3.9x、相对 DDlog 22x、相对 Ascent 14x；Polonius 上相对 Soufflé 5.9x、相对 DDlog 13x、相对 Ascent 3.3x。内存上比 DDlog 低很多，但相对 Soufflé 在 DOOP 上约 2x，是为增量维护付出的权衡。

**可迁移价值**：可用于构造 Code Agent 的“持续静态分析记忆”：agent 每次编辑代码后只增量更新事实和告警，把分析输出作为可验证环境反馈。

**局限**：论文是静态分析基础设施，不直接评估 LLM agent；迁移到 Python/TypeScript/Rust repo 修复流程还需要上层适配。

### 4. KernelScript: Cross-Boundary Typed DSL for eBPF Applications

- 方向：Code Agent / typed DSL / execution boundary safety
- 综合分：4.04
- 链接：https://arxiv.org/abs/2607.23900
- 证据来源：PDF 前 8 页。

**问题背景**：eBPF 应用同时跨 kernel code、userspace loader 和 shared maps。传统 C/libbpf 工作流里，跨边界类型和事件定义很容易漂移，代码仍能编译甚至通过 verifier，但运行时会悄悄腐坏共享状态。

**核心方法**：KernelScript 用一个 typed DSL 统一描述 maps、program handles 和 execution domains，再编译到标准 C 并继续使用原有 clang、bpftool、kernel verifier 工具链。它不替代 verifier，而是在 verifier 之前捕获跨边界关系错误。

**创新点**：这对 Agent 工具沙箱很有启发：很多工具调用错误不是单文件语法错，而是 host/runtime、前后端、schema/map、loader/kernel 之间的契约不一致。把跨边界契约提升到 typed DSL，可以让 Code Agent 在生成或修改系统代码时更早得到结构化错误。

**实验与 benchmark**：论文在 43 个 eBPF workload 上评估，覆盖 XDP、TC、kprobe、tracepoint、struct_ops。PDF 报告 KernelScript 能在编译期拒绝 C/libbpf 会构建并加载的 cross-boundary bugs；跨边界变更 diff 缩小约 5x；27 个 single-program path 和多类 runtime path 在真实 kernel 上通过，生成 XDP pass 的运行时间与手写 baseline 接近。

**可迁移价值**：可迁移到 Agent runtime 的工具接口设计：用 typed boundary 防止 agent 生成“本地看起来对、跨进程/跨环境就坏”的代码。

**局限**：领域是 eBPF；对普通 Web/后端仓库的收益取决于能否建立类似的跨边界类型系统。

### 5. Formally Verified Synthesizable Floating-Point Data Types in ARCH HDL

- 方向：Code Agent / verified code generation / HDL
- 综合分：3.93
- 链接：https://arxiv.org/abs/2607.23715
- 证据来源：PDF 前 8 页。

**问题背景**：ARCH HDL 的目标之一是让语言模型从自然语言规格生成硬件描述。硬件生成比普通代码生成风险更高，因为 SystemVerilog、SMT model 和证明模型一旦漂移，测试通过也可能掩盖语义错误。

**核心方法**：论文把 FP32/BF16 运算写成一个 host-language embedded DSL 描述，再从同一数据流图渲染到三种后端：synthesizable SystemVerilog、SMT-LIB 和 Lean 4 proof model。这样硬件、形式模型和证明模型共享结构，只剩每个 node 的打印器需要维护。硬件侧还用 Yosys 读回 SystemVerilog，并由 solver 证明它与 SMT model 等价。

**创新点**：它给 Code Agent 生成高风险代码提供了一个强约束模式：不要让模型直接分别写实现、规格和证明，而是让模型尽量生成单一中间描述，再由可信 compiler 派生多种产物。

**实验与 benchmark**：论文报告覆盖 FP32/BF16 comparisons、conversions、add/sub/mul/fma 等运算；部分可穷尽验证，FP32 mul/fma 等乘法相关运算用 Lean algebraic lifting 证明 correctly rounded。PDF 前 8 页未给传统 benchmark 表，但给出了验证覆盖范围和例外：BF16 fma 有一个 deliberate exception。

**可迁移价值**：适合用于 Code Agent 安全生成：让 agent 输出 IR/DSL，由编译器生成代码、模型和证明，再由 solver/测试闭环确认。

**局限**：HDL/浮点验证领域很窄，工程成本高；不适合所有日常代码生成任务。

### 6. Benchmarking Zero-Shot LLM-Generated Parent Selection in Genetic Programming for Symbolic Regression

- 方向：General Agent / LLM-generated operators / evaluation protocol
- 综合分：3.91
- 链接：https://arxiv.org/abs/2607.23505
- 证据来源：PDF 前 8 页。

**问题背景**：遗传编程里的 parent selection 会影响探索、利用和复杂度控制。论文问的是：LLM 能否在没有示例、没有迭代 meta-evolution 的情况下，一次性合成有效选择算子。

**核心方法**：作者固定 GP 框架中除 parent-selection operator 外的所有组件，让 8 个 LLM 用同一个自然语言 prompt 生成算子。每个模型生成 10 个 zero-shot operator，然后在同一预算下与 automatic lexicase 和 tournament selection 比较。

**创新点**：虽然任务不是 Agent，但它是一种很干净的“LLM 生成算法组件，然后插入可执行系统验证”的协议。对 Agent 训练数据构造来说，可以借鉴它的隔离变量方式：只替换 agent 生成的一个 policy/operator，其他环境和预算固定，最后看泛化表现。

**实验与 benchmark**：PDF 摘要和前几页说明使用 12 个 OpenML regression benchmark；Claude Sonnet 4.6 和 Gemini 3.1 Pro 整体表现较强，最强的 Kimi K2.5 zero-shot operator 超过 automatic lexicase 和 tournament baseline。前 8 页没有完整数值表，因此不展开未核实数值。

**可迁移价值**：可用于评估 LLM 生成 search policy、tool scheduler、test prioritizer、patch ranking heuristic 等组件，而不是只评估最终回答。

**局限**：符号回归和 GP 与工具 Agent 有距离；结果可能对 prompt 和 GP 框架很敏感。

### 7. Program Analysis with Prophecy and History Variables in the Nexis Compiler

- 方向：Code Agent / verified program analysis
- 综合分：3.85
- 链接：https://arxiv.org/abs/2607.23033
- 证据来源：PDF 前 8 页。

**问题背景**：很多程序优化需要知道“未来会发生什么”，传统数据流分析通常引入 CFG、抽象/具体化函数、Galois connection，以及前向/后向分析组合。论文尝试用 prophecy variables 和 history variables 直接绑定到 operational semantics。

**核心方法**：作者定义一个 DSL，把 prophecy/history variable 的子集约束加到基础 operational semantics 的 step rule 上，使优化正确性证明可以写成原程序和变换后程序之间的 forward simulation。论文还在 Nexis compiler 中实现，并用于 partial dead code elimination 和 lazy code motion。

**创新点**：对 Code Agent 的启发是，程序分析证据可以更贴近执行语义，而不只是文本 pattern 或 CFG 近似。尤其在自动修复/优化任务中，agent 如果能调用这类语义化分析器，就能给出更可验证的“为什么这段代码可移动/可删”的依据。

**实验与 benchmark**：PDF 前 8 页强调这是 verified implementation，并声称给出了 partial dead code elimination 与 lazy code motion 的首个 machine-checked correctness and optimality proofs；证明用 Lean 4 机械化。前 8 页没有常规性能 benchmark。

**可迁移价值**：适合作为 Code Agent 的证明型工具组件，用于高风险重构、优化和编译器代码修改。

**局限**：形式化门槛高，短期更像底层工具研究，不是直接可用的通用 Agent benchmark。

### 8. Novel Claim or Déjà Vu? Rethinking "Contamination-Free" Dynamic Evaluation for Multimodal Automated Fact-Checking

- 方向：Search Agent / fact-checking / dynamic benchmark contamination
- 综合分：4.39
- 链接：https://arxiv.org/abs/2607.23514
- 证据来源：PDF 前 8 页。

**问题背景**：多模态事实核验应该检索并推理外部证据，但静态 benchmark 可能已进入 LLM 参数记忆。动态 benchmark 常用“模型 cutoff 之后的新 claim”来避免污染，但这篇论文指出，新 claim 也可能由旧事件、旧证据或可推断常识构成，模型仍能绕过检索。

**核心方法**：作者采用 AVeriTeC 的 evidence sufficiency pipeline：让目标 LLM 直接从内部知识生成证据，再用文本/语义相似度与 oracle evidence 对齐，估计 claim-level contamination。它比较 SOTA 静态 AVeriTeC 和新构建的 ClaimReview2025Q4，并分析污染如何改变 MAFC performance、retrieval trajectory 和模型排名。

**创新点**：关键不是又做一个 fact-checking 数据集，而是把“是否真的需要检索”变成可测指标。对 Search Agent 评测非常重要：如果一个模型凭参数记忆就能答对，benchmark 不能证明它会查询规划、网页浏览、证据筛选和引用验证。

**实验与 benchmark**：论文报告动态评测能降低但不能消除污染；在 ClaimReview2025Q4 中，17.09%-29.30% 的 post-cut-off claim 仍有污染风险。污染可把 Macro-F1 最高抬高 11.34 个点，并改变模型排名；在统一 contamination-controlled 子集上，DeepSeek-V3.2 Macro-F1 最高为 55.93%，所有模型均低于 56% Macro-F1。

**可迁移价值**：Search Agent benchmark 构建时应加入“内部知识足够性检测”：先测 claim 是否能被模型无检索解决，再把这类样本过滤、降权或单独报告。训练时也应保留 query reformulation、evidence exploration 和证据覆盖度，而不只看 final answer。

**局限**：污染检测依赖相似度阈值和 oracle evidence；PDF 前 8 页说明 semantic overlap 会比词面 overlap 捕获更多风险，但仍可能漏掉隐性污染。

### 9. State-dependent error correlations shape voting thresholds in committees of AI agents

- 方向：General Agent / multi-agent verification / LLM committee design
- 综合分：4.16
- 链接：https://arxiv.org/abs/2607.23931
- 证据来源：PDF 前 8 页。

**问题背景**：很多系统用多个 LLM/Agent 做事实核验、代码审查或模型裁判，然后投票。但经典投票收益通常假设错误独立，而 LLM 很容易在同一类样本上共同犯错。多数投票可能没有想象中稳。

**核心方法**：论文把 agent vote 建模为带状态依赖相关性的 Gaussian-copula screening model。好样本和坏样本可以有不同相关结构，阈值规则不再只看单 agent 准确率，还要看共同错误如何影响 false accept/false reject 成本。

**创新点**：它把“多模型投票”从经验 trick 变成可估计的设计问题。对 Agent 系统来说，关键启发是：committee 里模型越多不一定越好，若错误高度相关，新增 agent 只会重复同一种错误；阈值应按任务状态和错误相关性调节。

**实验与 benchmark**：作者收集 28 个语言模型在 4 个 binary-screening benchmark 上的 174,384 次投票，任务包括 fact verification、GSM8K 数学解验证、MBPP code review 等。用 odd-indexed items 估计参数，在 even-indexed items 上预测 committee loss。full-matrix dependence model 的 identity-line R2 从 independence 的 0.840 提升到 0.967；cost-sensitive 阈值从 majority 的 scaled loss 60.25 降到 independence 52.50，再到 dependence-aware 50.77。

**可迁移价值**：适用于 Search/Code Agent 的 reviewer ensemble：记录模型间相关错误，按样本类型选择阈值，而不是默认多数投票。也适合训练 judge 时增加“错误多样性”指标。

**局限**：研究对象是固定投票委员会，不覆盖带通信、辩论、工具调用的复杂 multi-agent workflow。

### 10. Context-Adaptive Inference: A Unified Statistical and Foundation-Model View

- 方向：General Agent / context adaptation / routing and retrieval
- 综合分：3.77
- 链接：https://arxiv.org/abs/2607.23304
- 证据来源：PDF 前 8 页；论文较长，前 8 页主要覆盖定义、目录和问题框架。

**问题背景**：现代系统需要根据当前上下文改变预测：RAG 要随证据变化，Mixture-of-Experts 要路由到不同专家，临床模型要因病人状态调整推断。论文把这类能力统称为 context-adaptive inference。

**核心方法**：论文尝试统一统计学习和 foundation model 视角，把“先使用当前上下文信息，再做预测”的系统放到同一框架下讨论。对 Agent 来说，这相当于把检索证据、工具状态、用户历史、环境观测、memory compression 都视作影响推断策略的 context。

**创新点**：它不是单个 Agent 系统，而是概念框架。可取之处在于提醒我们：Agent post-training 不应只训练一个固定 policy，而要训练模型根据 context 选择推理深度、工具调用、检索范围、专家路由和拒答策略。

**实验与 benchmark**：PDF 前 8 页未覆盖具体实验表或 benchmark，因此本文按综述/框架论文处理，不摘录未核实数值。

**可迁移价值**：可作为 General Agent 系统设计的 related work：把 RAG、MoE、test-time adaptation、contextual decision 统一到“上下文改变推断”这个问题。

**局限**：前 8 页可核实信息有限；对具体训练流程的直接操作性弱于前几篇系统论文。

## 今日重点趋势

1. Code Agent 正在从“文本补丁生成”走向“可诊断执行闭环”。Triton kernel 论文最典型：反馈不只是 pass/fail，而是 profiling、IR、compiler pass 和验证结果组成的证据链。
2. Search Agent benchmark 需要显式去污染。动态数据并不自动等于真实检索能力，必须检测模型是否能仅靠参数知识覆盖 oracle evidence。
3. 多 Agent 投票需要建模相关错误。多数投票不是免费增益，错误同质化会留下正的 error floor。
4. Prompt/DSL/typed boundary 继续成为 Agent runtime 的基础设施方向。让模型生成高层声明，再由编译器或类型系统落实执行，比直接生成脆弱长 prompt 或跨边界代码更稳。

## 潜在研究 idea

- 构造 Code Agent 训练样本时，把每次失败拆成 `symptom -> diagnostic tool -> structured evidence -> patch hypothesis -> verification`，而不是只保存最终 patch。
- 为 Search Agent benchmark 增加“无检索内部知识证据覆盖率”字段；高污染样本不进入主榜，只用于记忆诊断。
- 在多模型 reviewer 中估计 pairwise error correlation，并把阈值从固定 majority 改为按任务状态、错误成本和相关性动态选择。
- 设计 Agent prompt DSL：任务约束、工具 schema、输出类型和验证器分离，由 compiler 生成不同模型/上下文长度下的具体 prompt。
