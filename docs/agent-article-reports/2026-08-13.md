## Code Agent

### 1. The Devil Is in the Interface: Evaluating How Tool Architecture Shapes Coding Agent Behavior

- 问题背景：许多 coding agent 研究把注意力放在“给模型更多能力”，例如代码检索、程序分析或多候选搜索，但这篇论文问的是另一个更底层的问题：即使底层能力相近，工具如何被组织、命名、暴露给模型，也会改变 agent 的行为。对真实 Code Agent 来说，这直接关系到工具 schema、接口抽象层级和 token 成本。
- 核心方法：作者构造 6 种工具架构：BashOnly、Atomic、NLSearch、Python、HypoTrack、Scratchpad，并尽量保持底层能力相同，只改变接口组织方式。评测覆盖 SWE-bench Live 的 65 个 repository-level issue，每个 actor/setup/instance 跑 10 次，三类 actor 包括 Qwen3Coder-30B、Kimi-K2.5、Claude Sonnet 4.5，总计 11,700 条轨迹。
- 创新点：它把 tool capability 和 tool architecture 拆开，证明“接口形态”本身就是 agent 系统设计变量。Atomic 工具不是增加新能力，而是把常见低层动作封装为更清晰的原语；NLSearch 也不用 embedding，而是用同模型子代理通过 bash 搜索，隔离自然语言搜索接口的影响。
- 实验与 benchmark：Atomic 在三种 actor 上都提升 repeated-attempt consistency，Qwen3Coder-30B 的 pass^9 从 0.020 提到 0.094。NLSearch 让仓库读取多样性提高约 13.4% 到 21.3%，并提升高相关文件 recall，但会带来噪声。Python CodeAct-style 接口在相近任务表现下减少 41.6% steps 和 56.3% token cost。Scratchpad/HypoTrack 这类轻量文本脚手架效果有限。
- 可迁移价值：可直接指导 Code Agent 工具 API 设计和后训练环境设计。低层高频动作应以结构化工具降低交互错误；自然语言检索适合扩大探索但需要 precision gate；Python/CodeAct 适合批量文件操作和成本压缩。
- 局限：论文刻意控制能力差异，因此不是在比较最强产品系统；NLSearch 的实现与真实 embedding search 不同，结论应解释为接口抽象效应。
- 阅读建议：强烈建议精读。它是本期最直接服务于 Code Agent 工具架构和训练轨迹设计的论文。
- 证据来源：arXiv PDF 前 8 页和摘要。

### 2. GraphAlignCoder: Aligning Program and Proof Graphs for Code Generation

- 问题背景：代码模型经常生成语法合理、可运行但不满足隐藏语义约束的程序。单纯 execution feedback 只能告诉模型最终失败，不能告诉它正确程序内部应该怎样组织分支、循环、返回值和约束。
- 核心方法：GraphAlignCoder 从正确 Python 解中抽取 implementation graph，包括 AST、control/data flow、guard、loop、return 等区域；同时用受约束的 Lean pipeline 生成 proof-flow graph，把 proof state、subgoal、tactic transition 转成显式正确性结构。训练分两步：先让模型同时学习代码、验证角色和 region-grounded obligations，再做 verification-to-code consolidation，把结构知识压回普通 Python 生成。
- 创新点：它不是让模型在推理时输出证明，而是把形式化证明结构作为训练期过程监督。直观地说，它把“为什么这个代码结构正确”压进模型参数，部署时仍然只输入普通编程题。
- 实验与 benchmark：模型基于 Qwen3.5-4B-Base LoRA。LiveCodeBench v6 上 GraphAlignCoder 解出 50/175，CodeRL 为 38；BigCodeBench Hard 上 23/148，CodeRL 为 16；BigCodeBench Full 上 363/1140，略高于 CodeRL 的 359。结构注入把 LiveCodeBench v6 从 33 提到 44，完整模型进一步到 50。
- 可迁移价值：对 Code Agent 后训练很有用：可以把测试失败轨迹、程序依赖图、证明/断言义务转成 region-level supervision，而不是只给 pass/fail reward。适合训练更稳的 patch generation 和边界条件处理。
- 局限：当前是 function-level/algorithmic generation，不是 repository-level issue 修复；Lean proof-flow 由 GPT-5.2 teacher 构造，成本和可靠性需要进一步验证。
- 阅读建议：建议作为“形式化结构监督 + 代码生成”方向重点跟进。
- 证据来源：arXiv PDF 前 8 页和摘要。

### 3. RealisticTritonBench: A Benchmark for Triton-Kernel Generation in Real-World AI Frameworks

- 问题背景：现有 Triton kernel benchmark 多是孤立的 PyTorch-to-Triton 翻译，只看单 kernel 正确性和速度，容易忽略真实 AI framework 中的端到端准确率、延迟和 evaluation hacking。
- 核心方法：RealisticTritonBench 从真实开源 AI framework 的 Triton 相关 PR 构造 31 个任务，输入包含任务描述、仓库上下文和目标函数定义。生成代码会替换原框架实现，再跑 unit tests、model accuracy tests 和端到端 latency tests。评估 scaffold 使用 mini-SWE-agent，强调真实仓库上下文里的 kernel 修改、优化和新增。
- 创新点：它把 kernel 生成从“写一个函数”推进到“修改框架里的可部署 kernel”。成功标准同时要求 UTP 达到 gold patch、模型数值鲁棒性不退化、TTFT/TPOT 不显著变慢。
- 实验与 benchmark：评估 DeepSeek-V3.2、Qwen3.5-397B-A17B、GPT-5.4、Gemini-3.1-Pro-Preview 等模型，平均任务成功率只有 18.71%，平均 FTP 43.23%，UTP 60.33%，数值鲁棒性 47.65%，端到端速度整体接近或低于 1x。Qwen3.5-397B-A17B 最高成功率 25.81%。失败主要来自 Triton API/类型/内存访问约束、真实仓库 kernel 语义理解不足、以及忽视数值稳定性和性能。
- 可迁移价值：非常适合 Code Agent benchmark 设计：把单元测试、模型准确率、系统延迟组合成多维 reward，避免 agent 只优化 visible tests。也能用于训练“读框架上下文-改 kernel-跑系统级验证”的闭环轨迹。
- 局限：任务数 31 个，领域集中在 Triton/GPU kernel；需要 GPU 环境，复现实验成本高。
- 阅读建议：建议加入 Code Agent benchmark related work，尤其是关注系统级验证和 reward hacking 防护。
- 证据来源：arXiv PDF 前 8 页和摘要。

### 4. The Next Challenge for Agentic Cybersecurity: A Realistic, Contamination-Free Reverse Engineering Benchmark

- 问题背景：很多安全 agent 在有源代码时表现快速进步，但真实安全分析经常面对 binary、firmware、malware 和 proprietary application。逆向工程要求先恢复程序语义，公开源代码改造的 benchmark 会有严重 contamination 风险。
- 核心方法：SRE-Bench 用 5,000+ 专家小时 clean-room 构造 19 个私有真实规模程序，平均 16,915.8 LOC，覆盖 network protocol、game、file format、malware、firmware。再加入 44 个自研 anti-analysis primitives，形成 262 个 binary instances，每个 6 个确定性评分任务，共 1,572 个任务。
- 创新点：它同时满足污染控制和真实规模两个条件。作者还做 adversarial reward-hacking audit，发现并修补可以不做真正 RE 就得分的捷径。
- 实验与 benchmark：评估 GPT-5.6-sol、Claude-Opus-5、GPT-5.5、Grok-4.5、GLM-5.2，整轮成本 $31.4K。最强 GPT-5.6-sol 平均 3.69/6，即 61.4%，只完整解决 80/254 个 gradeable instances；Claude-Opus-5 为 31.8%，GPT-5.5 为 17.1%。保护层会显著压低分数，说明 source-code security 能力没有自然迁移到 binary RE。
- 可迁移价值：对 agentic cybersecurity 和 Code Agent benchmark 都重要：真实任务不能只用公开小题；污染控制、规模、反捷径审计和确定性 grader 是 benchmark 的基本工程要求。
- 局限：成本极高，部分细节必须保密以维持 contamination-free；外部研究者复现难度可能较大。
- 阅读建议：建议作为 agent benchmark 构造方法论阅读。
- 证据来源：arXiv PDF 前 8 页和摘要。

### 5. Harnessing LLMs for Document-Guided Fuzzing of Python Libraries

- 问题背景：Python/DL/scientific libraries 的 API 输入约束复杂，包括类型、shape、数值范围和参数间依赖。现有 LLM fuzzing 常让模型直接生成完整测试程序，约束没有被结构化保存，也难以验证和复用。
- 核心方法：VistaFuzz 让本地开源 LLM 从 API 文档和 signature 中抽取 ParamSpec，记录参数类型、shape、范围、默认值，以及三类归一化参数关系：shape following、rank-bounded axis、type following。随后用 signature validation 去除 hallucinated/stale 参数，再生成满足约束的测试输入，配合 crash oracle 和 NaN oracle。
- 创新点：关键在把文档知识变成可机读、可验证、可复用的约束对象，而不是把 LLM 放在每次 fuzz campaign 的生成闭环里。这样成本随 API surface 增长，而不是随测试预算增长。
- 实验与 benchmark：覆盖 12 个 Python libraries、7,718 个 APIs。40.1% API 存在 inter-parameter relationships；禁用关系解析时，相关 API 的 valid generation rate 从 95%+ 降到 31.6%-52.8%。共报告 74 个 issue，43 个被开发者确认，29 个已修复。与 DocTer/FreeFuzz 比较时，在 PyTorch/TensorFlow 上覆盖更多 API 和代码行。
- 可迁移价值：适合 Code Agent 的“文档到约束”工具链。可以把 API docs 抽成 ParamSpec，再让 agent 在修复、测试生成、库迁移时复用，减少无效调用和 hallucinated 参数。
- 局限：只执行三类归一化参数关系；复杂语义依赖仍保留在文档字段但不强制执行。
- 阅读建议：建议精读 ParamSpec schema、signature validation 和 relationship ablation。
- 证据来源：arXiv PDF 前 8 页和摘要。

### 6. Testing Deep Learning Library APIs via Cross-Framework Differential Fuzzing

- 问题背景：CPU-GPU differential oracle 只能发现跨后端行为不一致的问题；如果一个 API 在 CPU/GPU 上同样错，就没有信号。跨框架等价 API 提供了另一个 oracle。
- 核心方法：XAMT 通过 API alias 和 parameter-role normalization 构造跨库候选组，再用 canonical ordinary inputs 做 pairwise execution validation 和 group-level consistency check，只保留执行验证通过的 API groups。之后对这些 groups 做 variance-guided differential fuzzing，输入覆盖 ordinary、boundary、non-finite values。
- 创新点：它不需要指定某个 reference library，而是用执行验证后的多框架群组做差分比较。这样能发现“同一操作在不同深度学习库实现不一致”的缺陷。
- 实验与 benchmark：覆盖 PyTorch、TensorFlow、Keras、JAX、MindSpore、PaddlePaddle、Chainer。构造 676 个 execution-validated groups，包含 2,563 个 matched APIs，跨 74 种库组合。发现 72 个可独立复现 discrepancy cases，其中 4 个 crash、68 个输出不一致；72 个开发者报告中 25 个已确认，23 个已修复。
- 可迁移价值：对 Code Agent 自动测试很有启发：agent 不必只依赖项目内测试，也可以构造跨实现 oracle。尤其适合 tensor API、编译器、数据库、格式解析器等有多个实现的领域。
- 局限：等价关系由 alias/role/执行验证近似，不是完整语义证明；很多报告仍 pending。
- 阅读建议：建议和 VistaFuzz 成对阅读，一个从文档约束出发，一个从跨实现等价出发。
- 证据来源：arXiv PDF 前 8 页和摘要。

## General Agent

### 7. Total Recall at What Cost? Benchmarking the Serving Cost of Agentic Memory Systems

- 问题背景：长期对话 agent 常用 memory system 来避免每轮重发完整 transcript，但多数论文只报 recall/accuracy，不系统计入 ingest、retrieval、reflection、answer 等多阶段 LLM 调用成本。
- 核心方法：论文比较 Mem0、Hindsight、Mastra Observational Memory，与 rolling window 和 full transcript 两个基线，在两个 backbone、不同 reasoning effort、最多 400 turns 的对话上测成本，并在 LoCoMo 665 个问题上配对测准确率。成本模型把 message size 和 conversation depth 分开拟合：log(C+1)=a+p log(L+1)+q log(t+1)。
- 创新点：它证明 memory 系统成本不能只由对话长度和消息大小预测。full-history 和 rolling-window 的 held-out error 低于 6.5%，但 memory systems 的 LOOCV-MAPE 达 18%-69%，说明内部 memory state 和 pipeline 行为才是成本主因。
- 实验与 benchmark：准确率范围约 21%-54%。Mem0 准确率波动最大，Hindsight 在 100-turn reference cell 最贵；最低 cost-per-correct-answer 在不同 backbone 上不同：Mastra OM 在 gpt-oss-20b low 最低，Mem0 在 Gemma 4 26B A4B 更优。break-even 也高度依赖系统和 backbone，最便宜系统可立即或几十轮内低于 full-history，最贵系统 400 turns 内仍不一定划算。
- 可迁移价值：对 General Agent memory 设计非常直接。选择 memory 不应只问“能不能召回”，还要把 ingest/reflect/retrieve 的模型调用、reasoning effort、缓存命中和 break-even turn 纳入评估。
- 局限：成本 benchmark 用合成对话；准确率只在 LoCoMo 子集；Hindsight ingest backbone 未完全受 benchmark 控制。
- 阅读建议：建议作为 memory system 评估规范参考，尤其适合长程 agent 服务成本建模。
- 证据来源：arXiv PDF 前 8 页和摘要。

## Search Agent

### 8. Token-Level Credit Assignment Optimization for Generative Document Retrieval

- 问题背景：生成式检索把文档检索变成 autoregressive DocID generation，但评估信号在完整 DocID 生成后才出现。现有 RL 往往把同一个 sequence-level reward 分给所有 token，无法判断哪个 DocID token 把路径带向了相关文档。
- 核心方法：TCA 把 DocID 生成建模为 sequential decision process。先 SFT 学会 query-to-DocID，再用 frozen reference model 下 gold DocID 的 hidden-state trajectory 作为 dense target，对生成轨迹每个 token 计算与 gold trajectory 的相似度、长度惩罚和 exact-match bonus。优化器可用 TCA-GRPO 或 TCA-PPO，并通过 trie-constrained decoding 保证 DocID 合法。
- 创新点：它把 retrieval relevance reward 对齐到实际生成决策粒度。早期 DocID token 是“路由到文档空间某个分支”的动作，token-level advantage 比全序列同奖惩更适合这个结构化动作空间。
- 实验与 benchmark：在 MS MARCO document ranking 和 Natural Questions 上评估，DocID 包括 Title+URL 和 Product Quantization。MS MARCO 上 TCA-GRPO(TU) 的 R@1/MRR@10 为 39.60/51.10，高于 DDRO(TU) 的 38.24/50.33；NQ 上 TCA-GRPO(PQ) 的 R@1/MRR@10 为 50.02/56.10，高于 DDRO(PQ) 的 48.10/54.32。TCA-GRPO 在四种设置中比 TCA-PPO 更稳定。
- 可迁移价值：对 Search Agent/RAG 训练很有启发：搜索轨迹里的 query token、DocID token、点击/选择动作都可以做 step-level credit assignment，而不是只看最终答案是否正确。
- 局限：主要评估生成式检索模型，不是完整 web search agent；token reward 依赖 gold DocID trajectory 和 frozen reference。
- 阅读建议：建议作为检索 RL 和 search trajectory credit assignment 的重点论文。
- 证据来源：arXiv PDF 前 8 页和摘要。

### 9. DexterSQL: Deep Schema Exploration and Rule-based Correction for Text-to-SQL Generation

- 问题背景：非微调 Text-to-SQL 系统常有三类问题：粗粒度 schema 信息无法区分易混列，重复 SQL 生成错误没有被沉淀成规则，复杂问题的条件和关系容易被遗漏、幻觉或放错位置。
- 核心方法：DexterSQL 由三部分组成。Deep Schema Explorator 离线识别 ambiguous columns，分析列内分布、join-conditioned distribution、coverage、fanout、agreement，并生成 disambiguation notes；Rule Creator 在训练数据库上挖掘 gold SQL 与 generated SQL 的差异，把可迁移错误转成 database-agnostic correction rules；Multi-path SQL Generation 用 dependency-tree-based intermediate representation 保留问题结构，再结合 few-shot 和 divide-and-conquer 生成候选 SQL。
- 创新点：它把 schema linking 从名字/值匹配推进到数据分布和连接关系层面，同时把 LLM 的常见 SQL 错误沉淀成规则库。对 Search Agent 来说，这相当于把“检索到的表结构”变成可执行、可审计的决策依据。
- 实验与 benchmark：在 BIRD-Dev 上，DexterSQL 使用 GPT-OSS-120B 达到 67.6% execution accuracy，比已有非微调 Text-to-SQL 至少高 2.7%；使用 GPT-4o/GPT-5.2 分别达到 71.6%/72.2%，至少高 0.9%。论文也报告 Spider-Test 上非微调方法对比表，DexterSQL 达 84.4。
- 可迁移价值：适合构造数据库型 Search Agent：先离线探索 schema 和数据分布，生成 notes/rules，再让在线 agent 在小而可信的上下文里生成查询和修正。
- 局限：系统较复杂，很多步骤依赖 LLM-as-judge/LLM clustering；规则从训练数据库挖掘，跨域鲁棒性仍需长期观察。
- 阅读建议：建议关注 deep schema exploration 和 database-agnostic rule creation，而不只看最终 SQL 分数。
- 证据来源：arXiv PDF 前 8 页和摘要。

### 10. TRACES: A Benchmark for Epistemic Reliability in Scientific Reasoning by LLMs

- 问题背景：科学 agent 往往部署在没有下游形式化 verifier 的场景。传统科学问答 benchmark 测已知答案，无法测试模型是否会在不可靠论文、撤稿论文或伪科学前提下继续产出看似合理的研究计划。
- 核心方法：TRACES 构造 42 篇 retracted、fraudulent、pseudoscientific papers 的 probe corpus。每个 probe 用接近原文的 preamble 建立错误前提，再提出看似合理的 study-design request。评分包括 IFR-a：agentic 场景下只有拒绝才算通过；IFR-i：交互场景下拒绝或明确识别不可靠前提都算通过；EDI 衡量模型复现 withheld paper/field-specific details 的深度。
- 创新点：它测的是“模型遇到科学化错误前提时会不会继续行动”，不是百科知识或最终答案。IFR-a/IFR-i 的区分也很关键：带免责声明但继续给操作性方案，对自动化 agent 仍然是失败。
- 实验与 benchmark：覆盖 30 个模型、42 个 probes、每个 10 次。aggregate IFR-a 为 0.93，IFR-i 为 0.809；模型在 95% 非空回复中继续 engage untenable premises。30 个模型中 22 个在超过 90% 的 agentic probes 上失败；拒绝集中在少数高知名度主题，显示更像 topic-keyed safety，而非稳健 epistemic competence。
- 可迁移价值：对 Search Agent 和 scientific RAG 很重要。Agent 不仅要检索和总结文献，还要识别证据源是否可靠、是否该 abstain、是否不能把免责声明后面的操作性内容交给下游执行器。
- 局限：试点 corpus 42 篇；评分涉及人工/规则边界；它关注不可靠科学文献，不等价于所有事实核验任务。
- 阅读建议：建议作为 scientific search agent guardrail 和证据可靠性 benchmark 的参考。
- 证据来源：arXiv PDF 前 8 页和摘要。

## 相关补充

- Developing LLM-based Multi-Agent Systems in Software Engineering 没进 Top 10，但适合作为 MAS 工具选型综述阅读。它比较 20 个 MAS framework，并在 README summarization use case 上做定量/定性评估，指出基础协调、角色、消息处理覆盖较好，但 telemetry、benchmarking、monitoring、human-in-the-loop 仍不足。
- Sci-Surf 值得跟进：它把每日论文推荐、用户 intent profile verbalization、LLM reranking 和 multimodal blog-style digestion 结合起来。真实用户评估中，引入 verbalized profile 后 Rel.% 从 18.9% 提到 29.3%。这对本自动化日报本身也有参考价值。
- RecSys Factory 提出“autonomy at decision points, not over pipelines”，用 29 个 skill、PitfallStore、HITL card 和 event-driven execution 控制工业推荐系统 agent 的自主边界。论文自述多项证据是 case-study/author-recalled，因而没有进入 Top 10，但工程思想值得吸收。
- Beyond Trial-and-Error 的 Agentic Self-Improvement 用 DSG/CMQ、VTA 和 Bayesian optimization 做闭环视频生成优化。它是一个很清楚的 generate-evaluate-rewrite/search loop，不过领域偏 I2V，迁移价值低于本期 Top 10。

## 今日重点趋势

1. Code Agent 评测正在从“能不能写对一个函数”走向“接口形态、真实仓库上下文、系统级指标和污染控制”。
2. Search Agent/RAG 训练越来越重视过程级监督：DocID token credit、schema distribution notes、correction rules、source reliability 都是可训练信号。
3. Agent memory 的评估不能只看召回准确率，服务成本、break-even turn、backbone 与 reasoning effort 的耦合必须一起看。
4. 科学/安全/代码 benchmark 都在加强 anti-contamination 和 anti-reward-hacking，否则模型可能绕过真正推理。

## 潜在研究 idea

- 为 Code Agent 构建 tool-architecture ablation suite：同一底层能力，分别暴露为 bash、atomic tools、NLSearch、Python CodeAct，收集 consistency、exploration、token cost 和 failure mode。
- 把程序图、执行 trace、测试失败和 proof/contract obligations 合成 region-level supervision，用于 repository-level patch training。
- 为 Search Agent 设计 step-level credit assignment：query rewrite、retrieved doc、citation choice、answer span、abstention 每一步都有局部 reward。
- 给长程 agent memory 建一个 cost-aware policy：根据预期对话长度、message size、backbone、accuracy target 动态选择 rolling window、full history 或 memory system。
