## Code Agent

### 1. Scrouting: Cost-Aware Routing of Coding Agents by Scouting the Repository First

- 链接：https://arxiv.org/abs/2608.04804
- 方向：Code Agent / Repository Scouting / Cost-Aware Routing
- 评分：4.900
- 证据来源：arXiv PDF 前 8 页 + 摘要

**问题背景**：现有 coding-agent router 通常只看 issue 文本就决定用哪个模型修复，但仓库级任务的难点往往藏在代码结构、复现路径和测试可验证性里。只按 issue 路由会把“是否值得调用昂贵 frontier fixer”建立在很浅的信号上。

**核心方法**：论文提出 SuperScout：先由 7B searcher 探索仓库，生成结构化 handoff；handoff 中的复现声明经过 sandbox 验证，不可证实的声明会被剔除；随后把 searcher hidden states 与任务文本一起交给 resume-based router，在四个 frontier fixer 中选择。这里的关键不是让小模型直接修 bug，而是让它先低成本地形成“仓库体检报告”，再把可靠证据交给修复模型。

**创新点**：它把 coding-agent 路由从“读需求”推进到“先接触仓库再路由”。对后训练很有启发：router 的监督信号不应只包含 issue、模型选择和最终成败，还应包含探索轨迹、复现证据、sandbox 证伪和 handoff 质量。

**实验与 benchmark**：在 SWE-bench Pro Python slice 的 266 个任务上，SuperScout 解决 159/266，最佳单模型解决 158/266，但每个成功修复的成本约为最佳单模型的五分之一。论文也报告了重要消融：不使用 router、总是选择最便宜 fixer 但保留 handoff，在该 benchmark 上能打平 routed system，说明收益主要来自 scout handoff，而不是路由器本身。

**可迁移价值**：适合用于 Code Agent 训练数据构造：先训练轻量 explorer 产出可验证 handoff，再训练 fixer 使用 handoff 修复；也适合把“复现声明是否 sandbox-verified”作为 reward 或过滤器。

**局限**：当前结果强烈依赖 SWE-bench Pro Python slice；router 本身的增益在该设置下不明显。若部署到多语言、多构建系统仓库，还需要验证 scout 的探索覆盖率。

### 2. Active-SWE: Benchmarking Coding Agents for Proactive Bug Fixing without Issue Reports

- 链接：https://arxiv.org/abs/2608.04682
- 方向：Code Agent / Proactive Debugging / Benchmark
- 评分：4.750
- 证据来源：arXiv PDF 前 8 页 + 摘要

**问题背景**：SWE-bench 类 benchmark 通常给 agent 高质量 issue report、错误描述和定位线索，而真实工程中很多 bug 没有 issue，或者 issue 只在用户投诉后才出现。这样的评测会高估 agent 在主动发现和修复问题上的能力。

**核心方法**：Active-SWE 把任务从“根据 issue 修一个 bug”改成“没有 issue 引导时主动发现并修复多个 bug”。论文构造了 1,663 个任务，覆盖六类 bug，并提出 difficulty-aware task formulation pipeline 与 dual-track evaluation。核心是把定位、发现和修复拆开评估，避免 agent 只靠 issue 中的文件名、堆栈或期望行为走捷径。

**创新点**：它把 coding-agent benchmark 的入口条件从“人类已经诊断过的问题”移到更真实的 proactive setting。对训练闭环 agent 来说，这意味着轨迹必须包含探索策略、测试设计、异常发现、候选 bug 排序和修复验证，而不只是 patch 生成。

**实验与 benchmark**：论文在 1,663 个任务上评估多个 SOTA coding agents，结论是现有 agent 在无报告主动修复上表现明显受限，尤其是定位和发现记录 bug 的能力不足。该 benchmark 测的是 repository exploration、bug discovery、多 bug 管理和修复验证，而不是单一 issue resolution。

**可迁移价值**：可以作为 agent post-training 的任务生成模板：隐藏 issue report，只保留仓库、测试入口或模糊目标，让 agent 自行收集证据并提交修复。也适合评估“自动维护型 agent”是否真的能主动工作。

**局限**：前 8 页能确认任务规模和评测目标，但完整模型结果表未全部核验；需要进一步读附录确认六类 bug 的分布和具体评分细节。

### 3. EA-Graph: Artifact-Anchored Verification Memory for Coding Agents under Upstream Drift

- 链接：https://arxiv.org/abs/2608.04278
- 方向：Code Agent / Verification Memory / Long-Horizon Agent
- 评分：4.650
- 证据来源：arXiv PDF 前 8 页 + 摘要

**问题背景**：跨会话 coding agent 常用 prose notes 记录“某结论已验证”，但这些文字不会保存当时验证所依赖的程序状态。上游代码变化后，项目仍可能编译通过，但早先的验证结论已经失效。

**核心方法**：EA-Graph 把验证声明锚定到 artifact graph，而不是普通文本记忆。它把 artifact 作为一等节点，粒度可以细到子路径，并解析别名到 leaf definitions；每条 claim 都绑定到被观察的 artifact、验证方式和可重新检查的依据。这样当上游漂移发生时，agent 可以判断哪些旧声明需要失效、重验或迁移。

**创新点**：这篇把 agent memory 从“记住结论”改成“记住结论依附的可验证对象”。这对长期 coding agent 很关键：记忆系统不应只做向量检索，还要维护代码对象、测试、证据和版本之间的依赖。

**实验与 benchmark**：论文使用生成仓库构造带 ground truth 的行为到 artifact 映射。每个 world 包含 12 个模块和 96 个行为；评估包含 42 个 analyzed sessions、7 个 clean worlds 和 14 个 model-world 条件。结果支持有限但明确的结论：artifact-anchored memory 在困难漂移阶段比 prose notes 和无持久记忆更能帮助较小模型判断可证性。

**可迁移价值**：适合放入 coding-agent runtime：每次验证不要只写“测试通过”，而应记录具体文件、函数、配置项、输入、输出和测试命令。训练时也可以把“证据锚点是否仍有效”作为长程记忆任务。

**局限**：评估基于生成仓库，而不是真实开源项目；论文也承认这是为了避免 benchmark 泄漏和未知 ground truth。真实仓库中的动态依赖、构建缓存和外部服务会更复杂。

### 4. AdaptAgent: A Multi-agent, Domain-Guided Reasoning Framework for Code Adaptation

- 链接：https://arxiv.org/abs/2608.04459
- 方向：Code Agent / Code Adaptation / Multi-Agent
- 评分：4.515
- 证据来源：arXiv PDF 前 8 页 + 摘要

**问题背景**：开发者经常从 LLM 或 Stack Overflow 拿到代码片段，但真正困难的是把片段适配到目标仓库：访问控制、常量定义、异常处理、依赖、错误传播和项目风格都可能不同。简单复制会编译失败或语义错误。

**核心方法**：论文形式化 code adaptation problem：给定代码片段、功能意图、目标仓库和适配位置，生成能融入仓库的 patch。AdaptAgent 使用多 agent 架构：Summarizer 从问题和答案中提炼意图，Policy agent 注入领域知识和项目策略，其他 agent 负责定位、生成和检查适配改动。它不是让一个模型直接“改一下代码”，而是把论坛知识、仓库约束和适配规则拆成可协作的推理步骤。

**创新点**：它将 code agent 的任务从“从零生成”或“修已知 bug”扩展到“迁移外部代码到既有仓库”。这正是实际工程 agent 高频场景：复用代码片段时，必须把上下文差异显式建模。

**实验与 benchmark**：论文报告在真实 code adaptation dataset 上，AdaptAgent 在语义正确性上超过强 baseline，并产生更多可维护的改动。前 8 页展示了 Stack Overflow 示例：GPT-4 直接适配虽然解决编译问题，但保留了无关逻辑，功能仍不正确；AdaptAgent 通过领域规则避免这类失败。

**可迁移价值**：可用于构造 Code Agent 训练任务：输入外部 snippet、目标仓库位置和意图摘要，要求 agent 生成最小 patch 并解释适配原因。也适合把“项目策略”作为 agent 可检索 skill。

**局限**：完整结果表和 dataset 细节需要读后文；多 agent 流程可能增加调用成本，是否优于单 agent 加强检索需要进一步比较。

### 5. RepoProbe: Benchmarking Architecture-Aware Repository Comprehension with Checklists

- 链接：https://arxiv.org/abs/2608.04783
- 方向：Code Agent / Repository Comprehension / Evaluation
- 评分：4.465
- 证据来源：arXiv PDF 前 8 页 + 摘要

**问题背景**：许多仓库级 benchmark 以 bug report 为入口，模型可以依赖错误日志、文件名和局部堆栈线索，绕过真正的架构理解。另一个问题是 LLM-as-a-Judge 标量分数不稳定，难以说明模型到底懂了哪些组件关系。

**核心方法**：RepoProbe 设计 architecture-aware repository comprehension benchmark，重点评测模型是否理解仓库架构、模块职责和跨文件关系，而不是是否能直接打 patch。它还提出 Checklist-Based Verification Protocol，把答案拆成 objective checklist items 再逐项验证，减少单一标量评分的主观性。

**创新点**：这篇很好地指出了 Code Agent 的“edit bias”：模型过早生成修改，却没有先建立仓库心智模型。Checklist 验证把“理解质量”变成可审计对象，可作为 agent 在动手改代码前的强制阶段。

**实验与 benchmark**：论文评估了多个 SOTA 模型，并报告 checklist protocol 相比传统 scalar judging 提升评估可靠性。该 benchmark 测的是 repository explanation、架构关系识别和开发者面对的理解任务，而不是 defect localization。

**可迁移价值**：可以把 RepoProbe 式 checklist 插入 coding-agent 工作流：先回答架构问题，通过 checklist 后再允许编辑。训练数据也可把“理解清单”作为中间监督。

**局限**：前 8 页能确认任务设计与验证协议，但具体仓库规模、题型分布和完整模型排名需要继续读后文。

### 6. OctoLong: Mid-Training On Cross-Repository Code Contexts Enhances Long-Context Modeling

- 链接：https://arxiv.org/abs/2608.05141
- 方向：Code Agent / Long Context / Cross-Repository Training
- 评分：4.445
- 证据来源：arXiv PDF 前 8 页 + 摘要

**问题背景**：长上下文模型的训练数据常来自书籍、论文或单仓库序列化，但真实 agentic coding 经常跨仓库追踪依赖：库 API、调用方、实现、包管理和语言服务信息会跨项目分散。单仓库上下文不能充分训练这种跨边界依赖推理。

**核心方法**：OctoLong 是一个 cross-repository code context pipeline。它结合 AST parser、language server backend 和 package manager，递归检索代码引用和依赖实现，构造 dependency-rich long-context corpus。论文收集约 6.2B tokens 的跨仓库长上下文数据，并进行约 10B tokens instruction tuning。

**创新点**：它把长上下文训练从“塞更长文档”变成“构造真实代码依赖链”。对 Code Agent 来说，重要的不是上下文窗口长度本身，而是上下文中是否包含可解析的调用、定义、包和跨 repo 证据。

**实验与 benchmark**：论文称在 18 个强 long-context benchmark 上评估，覆盖大海捞针、仓库级代码理解和下游 agentic tasks，并提升 API 理解能力。前 8 页确认了数据规模、pipeline 和评测范围。

**可迁移价值**：适合作为 agent 训练数据构造思路：用语言服务器和包管理器生成“问题相关跨仓库上下文包”，而不是随机拼接 repo 文件。也可用于训练 agent 的依赖追踪和引用解析能力。

**局限**：前 8 页没有完整列出所有 18 个 benchmark 的结果；数据主要围绕 Python 生态和高质量 GitHub/SEART Hub 仓库，迁移到多语言生态还需验证。

### 7. CURATE: Leveraging LLM Agents to Compose, Catalog, and Deploy Reproducible Workflows

- 链接：https://arxiv.org/abs/2608.04270
- 方向：Code Agent / Reproducible Workflow / Human-in-the-Loop
- 评分：4.205
- 证据来源：arXiv PDF 前 8 页 + 摘要

**问题背景**：当前 coding agents 多聚焦生成代码，但科学工作流还需要组合模块、记录输入输出、部署、复现和分享。用户往往手工拼接脚本和依赖，导致复现实验困难。

**核心方法**：CURATE 使用 LLM agents 生成可执行 workflow modules，并通过 compose、catalog、deploy 阶段组织完整生命周期。系统把工作流表示为带输入输出的有向图，在关键阶段设置 checkpoint gates 让用户验证和修订，并提供 catalog 促进模块复用。

**创新点**：它把 coding agent 从“写脚本”扩展到“可复现工作流工程”。对 agent 训练有价值的地方在于：任务轨迹不只包含代码生成，还包含模块边界、I/O schema、依赖、用户检查点和部署产物。

**实验与 benchmark**：论文基于 SeBS-Flow benchmark suite 派生的 4 个 workflow 进行复现和适配，并比较 Claude Code、Codex 和 Kimi 等 agent 在 workflow generation 上的表现。前 8 页可确认其关注可复现科学/工程 workflow，而非单文件代码生成。

**可迁移价值**：适合转化为 Code Agent 的工程化任务：让 agent 生成的不只是代码文件，还要产出 workflow DAG、依赖说明、执行入口和复现实验记录。

**局限**：样例 workflow 数量较少；当前 prototype 中 memory 更偏被动，长期自动改进能力仍有限。

### 8. ExeCRE: Execution-Consistency Guided Reliability Estimation for Self-Correcting Code Generation

- 链接：https://arxiv.org/abs/2608.04439
- 方向：Code Agent / Self-Correction / Execution Feedback
- 评分：4.170
- 证据来源：arXiv PDF 前 8 页 + 摘要

**问题背景**：自纠错代码生成常用执行结果、参考代码或 LLM feedback 作为修正信号，但这些信号本身可能不可靠。错误的反馈会让正确代码被改坏，或让错误代码被进一步强化。

**核心方法**：ExeCRE 用 execution-consistency 估计候选代码可靠性，而不是直接相信测试或模型反馈。它将可靠性估计接入 self-correction pipeline，让系统在决定是否修正、如何修正前，先判断当前反馈信号是否可信。

**创新点**：这篇把“执行反馈”从二值 oracle 改成带置信度的信号源。对闭环 Code Agent 很重要：agent 不应机械地“测试失败就改、测试通过就停”，而应估计测试、参考实现和执行轨迹的可靠性。

**实验与 benchmark**：论文报告在 GPT-5.2 + LiveCodeBench 上，ExeCRE 提升有效性和稳定性，并将代表性 self-correction baseline 中误导性修正信号从 113.2 降到 14.0。论文还把同一可靠性估计策略用于 code-based mathematical reasoning，并观察到类似收益。

**可迁移价值**：可以用作 agent runtime 的验证层：每次执行反馈进入 planner 前，先打 reliability score；训练时也可以把“是否应相信这个反馈”作为显式监督。

**局限**：前 8 页主要覆盖方法动机和关键结果，完整 benchmark 设置、任务分布和不同模型下稳定性需要继续读完整论文。

### 9. MemoryCPT: An End-to-End Agent Memory Framework for Cost-Performance Trade-off

- 链接：https://arxiv.org/abs/2608.04843
- 方向：General Agent / Agent Memory / Cost-Performance
- 评分：4.360
- 证据来源：arXiv PDF 前 8 页 + 摘要

**问题背景**：长程 LLM agent 需要从大量交互历史中取回有用证据，但取回越多，传给下游模型的 token 越多，成本也越高。现有 memory pipeline 常依赖手工启发式和多次 LLM 调用，容易产生冗余上下文。

**核心方法**：MemoryCPT 是端到端可训练的 agent memory pipeline，分为离线 memory construction 和在线 query-conditioned context generation。它结合 reciprocal rank fusion 与 LoRA summarizer，并用 GRPO 和 cost-aware reward 训练，在保持 downstream QA model 冻结的情况下优化“答案质量 / 推理成本”。

**创新点**：它把 agent memory 目标从“尽量找全”改成“单位成本产生多少有用智能”。论文提出 Quality per Cost (QPC)，显式衡量 answer quality 与 token/inference cost 的折中。

**实验与 benchmark**：论文在 LoCoMo 和 LongMemEval 上评估，报告 MemoryCPT 相比 baseline 改善质量-成本折中，并通过消融和敏感性分析刻画各组件贡献。LoCoMo/LongMemEval 测的是长对话、多会话或长记忆问答中能否恢复关键历史证据。

**可迁移价值**：适合作为长期 agent 的记忆压缩训练目标：不是简单 top-k retrieval，而是训练一个能按 query 生成最小充分上下文的 memory module。对工具使用 agent，QPC 也可扩展为“任务成功 / token+tool cost”。

**局限**：主要围绕 QA 式记忆评估；在真实多工具任务中，记忆可能影响计划、动作选择和安全约束，QPC 需要重新定义。

### 10. Skills Know Their Neighbors: Cluster-Contrastive Capability Pages for Skill Retrieval

- 链接：https://arxiv.org/abs/2608.04482
- 方向：General Agent / Skill Retrieval / Tool Routing
- 评分：4.345
- 证据来源：arXiv PDF 前 8 页 + 摘要

**问题背景**：agent 技能库变大后，很多技能主题和词汇相似，但可执行能力不同。普通检索器看到相近文本时，很难判断某个 skill 到底能解决哪些 query，不能解决哪些邻近 query。

**核心方法**：论文提出 Capability Pages，把每个 skill 的可执行区域、可解决 query 集合和与邻近技能的差异写成可检索页面。它包含正向能力描述和负向边界说明；检索 index 使用能力页提升 recall，executor 选择时使用负向说明降低误路由。

**创新点**：它把 skill retrieval 的错误归因从“embedding 不够强”转向“技能文本没有暴露可执行边界”。这很适合 Codex 类 skill 系统：每个 skill 文档不仅要写何时用，还要写相邻技能中哪些情况不要用。

**实验与 benchmark**：论文构建 SkillNet，包含 26,262 个 skills 和来自六个数据集的 5,400 个问题。Capability Pages 让 BM25、TF-IDF、BGE-M3 和两个 Qwen3-Embedding 检索器的 Recall@10 全部提升，平均提升 2.94 点；在四个 executor、六个数据集的 24 个组合上，加入负向边界使端到端任务成功率平均提升 3.62 点；中文 SSL-SkillDiscovery transfer 中 MRR@50 达到 73.07%。

**可迁移价值**：可以直接用于 agent skill 库维护：为每个工具/skill 生成 capability page，尤其标注近邻边界和不可处理任务。训练 tool router 时，也可以把 negative boundary 当作 hard negative。

**局限**：能力页质量依赖离线生成和聚类；当技能实现频繁变化时，需要同步更新能力边界，否则会引入过期路由信号。

1. Code Agent 评测正在从“给定 issue 修补”扩展到更真实的前置能力：先探索仓库、理解架构、主动发现 bug、估计反馈可靠性，再提交 patch。
2. Agent memory 的重点不再只是向量检索召回，而是成本约束、时间有效性、证据锚定和可重验性。
3. Skill/tool routing 的质量越来越依赖结构化元数据：handoff、capability page、negative boundary、sandbox verification 都比单纯文本相似度更关键。
4. 长上下文训练开始转向“结构化真实依赖链”，尤其是跨仓库代码引用，而不是随机延长文档。

## 潜在研究 idea

1. 构建“Scout-Then-Fix”训练集：对每个 SWE 任务保存 scout 轨迹、sandbox-verified reproduction claims、handoff 和 fixer patch，用于训练低成本 repository scout。
2. 把 EA-Graph 与 MemoryCPT 结合：长期 coding agent 的记忆既要按 artifact 锚定，又要按 query 生成最小充分上下文。
3. 为 tool/skill library 自动生成 Capability Pages：正向能力、负向边界、近邻技能差异、可执行前置条件都进入 router 训练。
4. 做 proactive SWE 后训练：隐藏 issue report，让 agent 从测试、日志、静态分析和用户模糊目标中主动发现 bug。
5. 给 execution feedback 加可靠性估计：把 ExeCRE 式 consistency score 作为 agent 是否继续修正的 gating signal。
